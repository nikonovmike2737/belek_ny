# BELEK NY: правило публикации только по содержательной дельте

Статус: HARD GATE. Обязательное правило для мониторинга, ручных продуктовых изменений и production release.

## Главное правило

Прод меняется только по содержательной причине. Допустимы два источника изменения:

1. подтверждённая дельта мониторинга относительно текущего опубликованного состояния;
2. последняя явная команда пользователя на конкретное продуктовое, UX, редакторское или документированное изменение.

Сам факт очередного запуска мониторинга, новое время проверки, новый run ID, повторная генерация эквивалентного PDF, служебная синхронизация или желание «освежить» артефакт содержательной причиной не являются.

Для scheduled monitor действует без исключений:

`NO DELTA = NO WRITE = NO COMMIT = NO DEPLOY`.

Явная пользовательская правка не превращается в ценовую дельту. Если пользователь меняет copy, UX, canon или другой непрейсовый слой, `previous_price_update_at`, `current_price_update_at`, ценовые стрелки и база цен остаются прежними, пока не опубликована реальная сопоставимая ценовая дельта.

## Приоритет источников

1. последняя явная инструкция пользователя;
2. актуальные canonical Google Drive HTML/PDF и `main`;
3. текущие binding rules и структурированные данные;
4. старые документы и исторические версии.

При конфликте старого документа с фактическим текущим продуктом нельзя молча вернуть старое поведение. Сначала синхронизировать документ с более приоритетным источником.

## Экономия GitHub Actions и один production commit

Для каждого следующего production release действует жёсткое правило:

`ONE RELEASE = ONE PRODUCTION COMMIT`.

До записи в `main` нужно собрать и проверить весь релизный state. Один итоговый production commit должен содержать все изменения, относящиеся к релизу, включая при наличии изменений:

- `index.html`;
- `belek_new_year_comparison_2026_2027_current.pdf`;
- `report/BELEK_NY_REPORT_SOURCE.html`;
- документацию и acceptance evidence;
- price/state-файлы;
- scripts/workflow/config, если они входят в scope того же релиза.

Запрещены отдельные production commits для HTML, затем PDF, затем документации, а также trigger-only, timestamp-only, docs-only, cleanup, housekeeping и post-release metadata commits.

Порядок работы:

1. на ветке/candidate или во временном рабочем состоянии собрать все изменения;
2. завершить HTML, PDF, docs, state и код до записи в `main`;
3. пройти обязательные проверки до production commit;
4. создать ровно один production commit;
5. GitHub Actions и Pages запускаются только от этого итогового commit, если их запуск действительно требуется;
6. post-prod smoke и release evidence не должны создавать второй commit только ради фиксации факта успешного deploy.

Если после production commit sync/validation workflow обнаруживает, что canonical Drive и tracked production artifacts расходятся, workflow должен завершиться FAIL, а не создавать автоматический второй commit. Исправление делается в следующем содержательном релизе либо через rollback, если обнаружен production defect.

Промежуточные candidate commits не должны сами по себе запускать production workflow. Не создавать отдельный GitHub Actions run только ради синхронизации, если итоговый production commit уже является достаточным триггером.

## Scheduled monitoring

Монитор стоимости номеров запускается два раза в сутки по московскому времени:

- 09:00 Europe/Moscow;
- 21:00 Europe/Moscow.

Проверка каждые 3 часа больше не используется.

Перед каждым мониторингом:

1. прочитать canonical HTML/PDF, `main`, структурированные данные цен, реестр категорий и разрешённые источники;
2. построить нормализованный слепок опубликованного состояния;
3. получить новый evidence;
4. сравнить одинаковые поля и одинаковый scope;
5. исключить служебные различия;
6. при пустой содержательной дельте остановиться без записи;
7. при подтверждённой дельте изменить только доказанный scope;
8. собрать согласованно HTML, PDF, docs/state, которые реально затронуты дельтой;
9. пройти проверки, readback и release gates;
10. создать один содержательный production commit со всем релизным state.

Trigger-only, timestamp-only, empty и housekeeping commits запрещены.

## Явная пользовательская продуктовая или редакторская правка

Если пользователь прямо поручил изменить продукт, это разрешённая содержательная дельта в пределах указанного scope. Для неё обязательна последовательность:

1. fresh-fetch canonical Drive HTML/PDF и live `main`;
2. проверить отсутствие параллельного drift;
3. сохранить rollback point;
4. внести только порученную дельту;
5. сохранить факты, цены и price timestamps, если пользователь не поручал их менять и нет новой подтверждённой ценовой дельты;
6. для пользовательского текста и flow пройти `docs/PUBLIC_COPY_QA_CHECKLIST.md`: Level A + Level B + Level C;
7. при любом материальном FAIL выполнить remediation, а не маскировать UX-дефект текстом;
8. проверить реальный rendered context, включая затронутые mobile/PDF поверхности;
9. записать canonical Drive-файлы IN PLACE с теми же file IDs;
10. сделать readback тех же IDs;
11. собрать все затронутые HTML/PDF/docs/state/code изменения в один итоговый release state;
12. только после PASS перенести тот же проверенный state в `main` ровно одним содержательным production commit;
13. дождаться Pages success и проверить публичный HTML/PDF;
14. сохранить acceptance и rollback evidence без второго служебного commit.

## Что считается содержательной дельтой мониторинга

- изменилась сопоставимая цена;
- изменилась сопоставимая доступность;
- добавилась, исчезла или переименовалась категория номера;
- изменились существенные условия питания, новогоднего ужина, обязательных доплат или отмены;
- изменились важные зимние услуги или инфраструктура;
- появились сильные новые доказательства, снимающие важную неопределённость;
- рейтинг или рекомендация изменились из-за подтверждённых новых фактов.

Повторная проверка того же источника без изменения пользовательского факта дельтой не является.

## Цены

Сравнение цены разрешено только для того же отеля, точной категории поставщика, того же состава гостей, дат, питания и валюты.

- `current > previous` -> `up` и красная `↑`;
- `current < previous` -> `down` и зелёная `↓`;
- `current == previous` -> `same`, стрелки нет.

Несопоставимые предложения не получают статус роста или снижения. Пакет с перелётом, трансфером, гольфом или другими услугами не подменяет цену проживания.

`previous_price_update_at` и `current_price_update_at` меняются только при реально опубликованной сопоставимой ценовой дельте по `docs/PRICE_UPDATE_TIMESTAMPS_RULE.md`.

## Официальные ссылки отелей

Канонические URL и языковой приоритет определяются отдельными binding rules. Изменение доступности источника само по себе не является ценовой дельтой и не даёт scheduled price monitor права переписывать prod вне его актуального prompt/scope.

Если пользователь отдельно поручил изменить ссылку или другой непрейсовый элемент, это выполняется как явная продуктовая правка с сохранением ценовых часов.

## Communication release gate

Любая затронутая публичная поверхность должна получить:

`Level A PASS + Level B PASS + Level C PASS`.

Функциональный smoke, unit tests и автоматический lint не заменяют Level B/C. Evidence хранится в `docs/EDITORIAL_COMMUNICATION_ACCEPTANCE_CURRENT.md` или в актуальном release-specific acceptance evidence, если scope будущего релиза требует отдельной записи.

## Поведение при отсутствии изменений

Если scheduled monitor не нашёл подтверждённой содержательной дельты, запрещено:

- менять видимое время обновления;
- менять внутреннюю версию ради публикации;
- пересобирать и заменять эквивалентный PDF;
- переписывать canonical Drive-файлы;
- трогать trigger-файлы;
- создавать commit только для запуска workflow;
- создавать пустой commit;
- запускать deploy только потому, что прошло время.

## Инвариант production release

Для мониторинга:

`published state -> confirmed delta -> complete HTML/PDF/docs/state -> gates PASS -> one production commit -> Pages -> post-prod verification`.

Для прямой пользовательской правки:

`explicit user instruction -> fresh published state -> bounded change -> complete HTML/PDF/docs/state -> A+B+C PASS -> Drive IN PLACE + readback -> one production commit -> Pages -> post-prod verification`.

Если соответствующей содержательной причины и зелёных gates нет, публикация запрещена.
